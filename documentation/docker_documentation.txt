1. PROJECT OVERVIEW
================================================================================

The EWS Retention Platform uses Docker and Docker Compose to define and run
multi-container Docker applications. The `docker-compose.yml` file orchestrates
the various services of the application, ensuring they can be built, started,
and managed together with ease and consistency across different environments.
This setup greatly facilitates development, testing, and deployment by
encapsulating each component within its own isolated container, providing
a reproducible environment for the entire application stack.

The platform consists of three containerized services:
- **Backend**: FastAPI application serving the REST API on port 8000
- **Scheduler**: Background job runner for hourly feature store updates
- **Frontend**: React application served on port 3000

2. DOCKER COMPOSE CONFIGURATION
================================================================================

--------------------------------------------------------------------------------
2.1 Full docker-compose.yml Content
--------------------------------------------------------------------------------

File: `docker/docker-compose.yml`

```yaml
version: '3.8'

services:
  backend:
    build: .
    ports:
      - "8000:8000"
    volumes:
      - ./models:/app/models
      - ./backend:/app/backend
    environment:
      - DATABASE_URL=sqlite:///./backend/ews_platform.db

  scheduler:
    build: .
    command: python -m backend.services.scheduler
    volumes:
      - ./models:/app/models
      - ./backend:/app/backend

  frontend:
    build: ./frontend
    ports:
      - "3000:80"
    depends_on:
      - backend
```

--------------------------------------------------------------------------------
2.2 Backend Service
--------------------------------------------------------------------------------

- **Service Name**: `backend`
- **Build Context**: `.` (the project root directory)
  - Docker Compose looks for a `Dockerfile` in the root directory to build
    the image. This Dockerfile should set up the Python environment, install
    dependencies from `requirements.txt`, and configure the FastAPI application
    to run with uvicorn.

- **Purpose**: Runs the FastAPI backend application. This service exposes
  50+ RESTful API endpoints including authentication, student management,
  risk predictions, ML inference, LLM-powered advice, analytics, business
  intelligence, and data integration.

- **Ports**: `8000:8000`
  - Maps container port 8000 to host port 8000.
  - Access the API at `http://localhost:8000`
  - API docs (Swagger UI) at `http://localhost:8000/docs`
  - Alternative docs (ReDoc) at `http://localhost:8000/redoc`

- **Volumes**:
    - `./models:/app/models`: Mounts the local `models` directory containing
      trained ML models (`.pkl` files for Random Forest and XGBoost),
      feature engineering scripts, and model configuration. This allows
      model updates without rebuilding the Docker image.
    - `./backend:/app/backend`: Mounts the local backend source code
      directory. Enables live code changes during development without
      requiring a full image rebuild (hot-reload with uvicorn `--reload`).

- **Environment Variables**:
    - `DATABASE_URL=sqlite:///./backend/ews_platform.db`: Sets the SQLAlchemy
      database connection string. Uses SQLite with the database file stored
      within the mounted backend volume, ensuring data persistence on the
      host filesystem.
    - Additional environment variables can be configured via `.env` file
      (see Section 4).

--------------------------------------------------------------------------------
2.3 Scheduler Service
--------------------------------------------------------------------------------

- **Service Name**: `scheduler`
- **Build Context**: `.` (the project root directory)
  - Uses the same Dockerfile as the backend service, sharing the Python
    environment and installed dependencies.

- **Purpose**: Runs a separate dedicated process for scheduled background
  tasks. This decouples long-running or periodic jobs from the main web
  server process, improving API responsiveness and stability.

- **Command**: `python -m backend.services.scheduler`
  - Overrides the default container command to run the scheduler module
    instead of the FastAPI server.
  - The scheduler module (`backend/jobs/feature_store_job.py`) uses the
    `schedule` library to run feature store precomputation every hour:
    ```python
    schedule.every(1).hours.do(run_feature_store_computation)
    ```
  - On startup, it runs one immediate computation, then enters the
    scheduling loop.

- **Scheduled Tasks**:
    - **Feature Store Precomputation** (hourly): Iterates all students in
      the database, computes engagement features via `FeatureStoreService`,
      and stores results in the `EngineeredFeatures` table for fast retrieval.
    - **Prediction Updates** (configurable via `PREDICTION_UPDATE_INTERVAL`
      environment variable, default 3600 seconds).

- **Volumes**:
    - `./models:/app/models`: Shares ML models with the scheduler, needed
      for model-based feature computations.
    - `./backend:/app/backend`: Shares backend source code for the scheduler
      module and all service dependencies.

- **No Ports Exposed**: The scheduler does not serve HTTP traffic.

--------------------------------------------------------------------------------
2.4 Frontend Service
--------------------------------------------------------------------------------

- **Service Name**: `frontend`
- **Build Context**: `./frontend` (the `frontend` subdirectory)
  - Docker Compose looks for a `Dockerfile` in the `frontend/` directory.
    This Dockerfile should handle Node.js environment setup, `npm install`,
    `npm run build`, and serve the production build via a web server (e.g.,
    nginx serving static files).

- **Purpose**: Hosts the React 18.2 frontend application. Serves the
  single-page application (SPA) including all JavaScript bundles, CSS,
  and static assets.

- **Ports**: `3000:80`
  - Maps container port 80 (standard HTTP, typically nginx) to host port
    3000. Access the frontend at `http://localhost:3000`.

- **Dependencies**: `depends_on: - backend`
  - Ensures the backend service starts before the frontend. This is critical
    because the frontend makes API calls to `http://localhost:8000/api/v1`
    for all data operations.

- **Frontend Technology Stack** (from package.json):
    - React 18.2.0, React Router v6.22.3
    - Bootstrap 5.3.8 + React-Bootstrap 2.10.10
    - Chart.js 4.4.2 + react-chartjs-2, Recharts 3.7.0
    - Framer Motion 12.31.0 for animations
    - Axios 1.6.8 for HTTP requests
    - React Window for virtualized lists

3. DOCKERFILE LOCATIONS (IMPORTANT NOTE)
================================================================================

During the documentation process, an explicit `Dockerfile` was not found
in the project root (`./`) for the `backend` and `scheduler` services,
nor was a `Dockerfile` found in the `frontend/` directory for the `frontend`
service.

**Based on the `docker-compose.yml` configuration (`build: .` and
`build: ./frontend`), `Dockerfile` files are *expected* to be present in
these respective directories for the Docker Compose build process to succeed.**

Their absence during inspection suggests the Dockerfiles are yet to be
created. To fully containerize the application, the following Dockerfiles
would need to be created:

**Expected Backend Dockerfile** (project root `./Dockerfile`):
```dockerfile
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "backend.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**Expected Frontend Dockerfile** (`frontend/Dockerfile`):
```dockerfile
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/build /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

7. USAGE AND WORKFLOW
================================================================================

To manage the EWS Retention Platform using Docker Compose, navigate to the
project root directory where `docker-compose.yml` is located.

**Non-Docker Local Setup (setup.sh)**:

A `setup.sh` bash script is provided for running the backend locally without
Docker. It:
1. Creates a Python virtual environment in `venv/` (skips if already exists)
2. Activates the venv
3. Installs all dependencies from `requirements.txt` using a custom TMPDIR
   (`/home/duffer/tmp`) to avoid `/tmp` space exhaustion on smaller partitions

```bash
bash setup.sh
source venv/bin/activate
uvicorn backend.main:app --reload
```

**Initial Docker Setup**:

1. Copy the environment configuration:
   ```bash
   cp .env.example .env
   ```

2. Edit `.env` and set required values:
   - `GEMINI_API_KEY` or `CLAUDE_API_KEY` (depending on `LLM_PROVIDER`)
   - `SECRET_KEY` (strong random string for JWT signing)
   - `INTEGRATION_API_KEY` (change from dev default before deploying)

3. Ensure Dockerfiles exist (see Section 3 for templates).

**Common Commands**:

- **`docker compose build`**:
    - Builds (or rebuilds) the Docker images for all services defined in
      `docker-compose.yml`. Run whenever `Dockerfile`s, `requirements.txt`,
      or `package.json` changes.

- **`docker compose up -d`**:
    - Starts all services in detached (background) mode. If images don't
      exist, it builds them first.
    - The backend starts on port 8000, frontend on port 3000, and the
      scheduler runs in the background.

- **`docker compose stop`**:
    - Stops running service containers without removing them.

- **`docker compose down`**:
    - Stops and removes containers, networks, and volumes created by `up`.
    - Use `docker compose down --volumes` to also remove named volumes,
      which might include persistent database data.

- **`docker compose logs -f [service_name]`**:
    - Displays log output from services. Use `-f` to follow in real-time.
    - Example: `docker compose logs -f backend` to monitor API requests.

- **`docker compose exec [service_name] [command]`**:
    - Executes a command inside a running container.
    - Example: `docker compose exec backend bash` to open a shell.
    - Example: `docker compose exec backend python -m backend.services.core.data_ingestion`
      to trigger manual data ingestion.

**Development Workflow**:

Since the `backend` and `frontend` source directories are mounted as volumes,
code changes on the host are immediately available inside the containers:

1. Edit code locally
2. Backend: uvicorn auto-reloads on file changes (if `--reload` flag is set)
3. Frontend: React dev server auto-refreshes in the browser
4. No image rebuild needed for source code changes

**When to Rebuild Images**:
- Adding new Python packages to `requirements.txt`
- Adding new npm packages to `package.json`
- Changing Dockerfile configuration
- Updating system-level dependencies
