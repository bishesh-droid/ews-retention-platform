1. OVERVIEW
================================================================================

This document provides a comprehensive catalog of all data files used in the
EWS Retention Platform, their purpose, structure, processing pipeline, and
the detailed implementation of the data ingestion system. The platform
processes raw Excel data files from institutional LMS and academic systems,
validates and transforms them, and loads them into a Star Schema analytical
database for risk scoring, predictions, and analytics.

Data flows through the system in this high-level path:

```
Raw Excel Files (data/raw/)
    → Data Catalog Generation (scripts/generate_data_catalog.py)
    → Schema Validation (backend/ingestion/schema_manager.py)
    → Row-Level Validation (backend/ingestion/row_validators.py)
    → Transformation & Normalization (backend/ingestion/transformers.py)
    → Star Schema Loading (DimStudent, DimCourse, Fact tables)
    → Feature Engineering (backend/services/feature_engineering.py)
    → Risk Scoring (backend/services/risk_scoring.py)
    → Decision Engine (backend/services/core/decision_engine.py)
```

- **Ingestion Function**: `_ingest_quiz_assignment_exam(db)`

--------------------------------------------------------------------------------

#### `Engagement_Analysis.xlsx`
- **Type**: Student-level engagement metrics
- **Purpose**: Primary LMS engagement data source. Contains two critical sheets:
  - **"Learner Usage main dump"**: Student enrollment data with 15 columns

- **Refresh Frequency**: Daily
- **Status**: Active
- **Ingestion Function**: `_ingest_engagement_data(db)` - This is the primary
  ingestion function that creates Student, Course, and Enrollment records.

#### `Learner usage week 3.xlsx`

- **Purpose**: Detailed activity metrics for a specific week
- **Student Identifier**: Expected `email` or `learner_id`

5. DATA QUALITY GUIDELINES
================================================================================

--------------------------------------------------------------------------------
5.1 Student Identifier Requirements
--------------------------------------------------------------------------------

All **student-level** data files MUST contain at least one of these
identifier columns:
- `email` (preferred)
- `learner_email`
- `Username`
- `student_id`
- `org_defined_id`

Files without student identifiers are treated as **aggregate** data and
processed through the separate reporting pipeline.

--------------------------------------------------------------------------------
5.2 File Naming Conventions
--------------------------------------------------------------------------------

**For Assessment Files**:
- Format: `{assessment_type}_{date}_FINAL.xlsx`
- Example: `graded_quiz_1_2025-02-10_FINAL.xlsx`
- Always include "FINAL" or "complete" in the authoritative version

**For Engagement Files**:
- Format: `{data_type}_{period}.xlsx`
- Example: `Learner_usage_week_3.xlsx`

**For Aggregate Reports**:
- Clearly indicate "Summary" or "Report" in filename
- Example: `BS_MSc_Live_Summary_Trimester_1.xlsx`

--------------------------------------------------------------------------------
5.3 Data Validation Rules
--------------------------------------------------------------------------------

All files undergo multi-layer validation:

**Schema-Level Validation** (`backend/ingestion/schema_manager.py`):
- Column count matches expected schema from `data_catalog.json`
- Required columns are present
- Data types match expected types

**Row-Level Validation** (`backend/ingestion/row_validators.py`):
- Required field presence (non-null checks)
- Excel error detection (`#DIV/0!`, `#VALUE!`, `#N/A`, `#REF!`, `#NAME?`)
- Numeric bounds checking (percentages 0-100, no negative scores)
- Timestamp sanity checks (dates within reasonable range)
- Email format validation (regex pattern matching)
- Column count validation per row

**Failed validation** → Rows sent to quarantine (`backend/ingestion/quarantine.py`)
with error details for later review and correction.

--------------------------------------------------------------------------------
5.4 Percentage Format Standard
--------------------------------------------------------------------------------

**Standard**: Store percentages as **decimals (0-1)**
- Example: 75% stored as `0.75`
- Validation: `0.0 <= value <= 1.0`
- Normalization: `backend/ingestion/transformers.py` handles both formats
  automatically:
  - Values > 1.0 are divided by 100 (assumed to be 0-100 scale)
  - Values in 0-1 range are kept as-is

--------------------------------------------------------------------------------
5.5 Missing Data Representation
--------------------------------------------------------------------------------

**Allowed representations**:
- Empty cell (null)
- `NA`
- `N/A`
- `-` (hyphen)

**Forbidden**:
- `0` to represent missing (unless actually zero)
- Random text strings
- Excel error values (`#DIV/0!`, `#VALUE!`, etc.)

6.1 Student-Level Data Processing Flow
--------------------------------------------------------------------------------

```
Raw Data File (.xlsx)
    |
    v
[Schema Validation] (schema_manager.py + data_catalog.json)
    |
    v
[Row-Level Validation] (row_validators.py, validators.py)
    |                |
    v                v
[Pass]            [Fail]
    |                |
    v                v

    |                v
    v            [Error Log] (error_logger.py)

    |
    v

    +-- DimStudent (canonical student dimension)
    +-- DimCourse (canonical course dimension)
    +-- Enrollment (student-course relationship)
```

```
    v
```

7. INGESTION PIPELINE - DETAILED IMPLEMENTATION
================================================================================

--------------------------------------------------------------------------------
7.1 Data Ingestion Service (backend/services/core/data_ingestion.py)
--------------------------------------------------------------------------------

**Purpose**: Master ingestion orchestrator. This is the primary entry point
for loading all raw data into the database.

**Key Function**: `ingest_all_data(db: Session)`
- **Idempotency**: Checks if data has already been ingested (student count > 0)
  and skips re-ingestion to prevent duplicates.
- **Orchestration**: Calls three sub-functions in sequence:

1. **`_ingest_engagement_data(db)`**:
   - Reads: `Engagement_Analysis.xlsx`
   - Parses two sheets:
     - **"Learner Usage main dump"**: Creates `Student`, `Course`, and
       `Enrollment` records. Extracts 15 columns per enrollment.
     - **"Courses"**: Reads course content requirement counts (week1, week2,
       lab) to populate the `Course.content_required` fields.
   - Creates or updates `Student` records (keyed by username/email)
   - Creates `Course` records (keyed by course_code)
   - Creates `Enrollment` records linking students to courses with all
     engagement metrics (content_completed, quiz counts, discussion activity,
     login counts, time spent, SCORM data)

2. **`_ingest_quiz_assignment_exam(db)`**:
   - Reads: Multiple XLSX files for graded academic data
   - Creates `GradedComponent` records (quiz and assignment scores with
     dates, component type, max score)
   - Creates `ExamRecord` records (exam marks, attendance status, max marks)

3. **`_update_enrollments_from_latest(db)`**:
   - Reads: Latest weekly engagement files
   - Updates existing `Enrollment` records with additional fields from
     the most recent data exports (login counts, time spent, discussion
     activity, SCORM completion data)

--------------------------------------------------------------------------------
7.2 Ingestion Pipeline (backend/ingestion/pipeline.py)
--------------------------------------------------------------------------------

**Purpose**: Reusable pipeline framework for processing any data file through
the validation-transformation-loading workflow.

**Class**: `EWSDataPipeline`

**Pipeline Phases**:

1. **Schema Validation Phase**:
   - Loads expected schema from `data_catalog.json` via `SchemaManager`
   - Validates column names, types, and counts
   - Rejects files that don't match expected structure

2. **Row Validation Phase**:
   - Iterates each row through `RowValidator`
   - Checks business rules (non-null required fields, valid ranges)
   - Routes invalid rows to `Quarantine`

3. **Transformation Phase**:
   - Applies `Transformers` to normalize data
   - Percentage normalization (0-100 to 0-1)
   - Type coercion (strings to numbers, dates)
   - Missing value handling

4. **Loading Phase**:
   - Inserts validated, transformed rows into the database
   - Records processing in `DataLineage` for audit trail
   - Ensures idempotency (checks for existing records)

--------------------------------------------------------------------------------
7.3 Row Validators (backend/ingestion/row_validators.py)
--------------------------------------------------------------------------------

**Purpose**: Business logic for validating individual data rows before
database insertion.

**Key Validation Functions**:

- `validate_row(row, schema)` → `(is_valid: bool, errors: list[str])`
  - Orchestrates all validation checks for a single row
  - Returns validation status and list of error messages

- `check_required_fields(row, required_columns)` → `list[str]`
  - Ensures required columns have non-null, non-empty values
  - Returns list of missing field names

- `check_excel_errors(row)` → `list[str]`
  - Scans all cell values for Excel error strings:
    `#DIV/0!`, `#VALUE!`, `#N/A`, `#REF!`, `#NAME?`, `#NULL!`, `#NUM!`
  - Returns list of columns containing errors

- `check_numeric_bounds(row, column, min_val, max_val)` → `bool`
  - Validates that numeric values fall within expected ranges
  - Used for percentages (0-100), scores (0-max_score), etc.

- `check_email_format(value)` → `bool`
  - Validates email addresses against standard regex pattern
  - Used for student identifier columns

- `check_timestamp_sanity(value, min_date, max_date)` → `bool`
  - Validates that dates/timestamps fall within reasonable bounds
  - Prevents obviously wrong dates (e.g., year 1900, future dates)

--------------------------------------------------------------------------------
7.4 Validators (backend/ingestion/validators.py)
--------------------------------------------------------------------------------

**Purpose**: Utility functions for common validation checks, used by both
the row validators and the pipeline.

**Key Functions**:

- `is_excel_error(value)` → `bool`
  - Checks if a single cell value is an Excel error string

- `is_within_bounds(value, min_val, max_val)` → `bool`
  - Generic numeric range check

- `is_valid_percentage(value, scale)` → `bool`
  - Checks if value is a valid percentage on given scale (0-1 or 0-100)

- `validate_column_count(row, expected_count)` → `bool`
  - Ensures row has the expected number of columns

--------------------------------------------------------------------------------
7.5 Transformers (backend/ingestion/transformers.py)
--------------------------------------------------------------------------------

**Purpose**: Data transformation and cleaning functions applied to validated
data before database insertion.

**Key Functions**:

- `normalize_percentage(value, input_scale='auto')` → `float`
  - Converts percentages to standard 0-1 scale
  - Auto-detects input scale: values > 1.0 assumed to be 0-100 scale
  - Returns normalized float in [0.0, 1.0]

- `coerce_to_numeric(value, default=None)` → `Optional[float]`
  - Attempts to convert string values to numeric
  - Handles common formats: commas, currency symbols, percentage signs
  - Returns default if conversion fails

- `coerce_to_date(value, formats=None)` → `Optional[datetime]`
  - Attempts to parse date strings in multiple formats
  - Default formats: ISO 8601, US, European, Excel serial dates

- `clean_string(value)` → `str`
  - Strips whitespace, normalizes unicode, removes control characters

- `handle_missing_value(value, strategy='null')` → `Any`
  - Applies missing value strategy: null, default, forward-fill, interpolate

- `TypeCoercer` class:
  - `coerce_int(value)` → `Optional[int]`
  - `coerce_float(value)` → `Optional[float]`
  - `coerce_bool(value)` → `Optional[bool]`
  - `coerce_string(value)` → `str`
  - `coerce_date(value)` → `Optional[datetime]`
  - `coerce_email(value)` → `Optional[str]` (lowercased, stripped)

--------------------------------------------------------------------------------
7.6 Quarantine (backend/ingestion/quarantine.py)
--------------------------------------------------------------------------------

**Purpose**: Manages storage of invalid or problematic data rows that fail
validation. Ensures data quality issues do not halt the ingestion process.

**Key Functions**:

- `quarantine_row(row, errors, source_file, sheet_name)`:
  - Stores the invalid row along with error details
  - Records source file and sheet for traceability
  - Timestamps the quarantine event

- `get_quarantined_rows(source_file=None, limit=100)` → `list[dict]`:
  - Retrieves quarantined rows, optionally filtered by source file
  - Returns row data, error messages, and metadata

- `release_from_quarantine(row_id)`:
  - Marks a quarantined row as reviewed/resolved
  - Used after manual correction

**Storage**: Quarantined rows are stored in `data/quarantine/` directory
as JSON files, one per ingestion batch.

--------------------------------------------------------------------------------
7.7 Schema Manager (backend/ingestion/schema_manager.py)
--------------------------------------------------------------------------------

**Purpose**: Works in conjunction with `data/data_catalog.json` to validate
that incoming data files conform to expected schemas before processing.

**Key Functions**:

- `load_schema(filename)` → `dict`:
  - Loads the expected schema for a specific file from the data catalog
  - Returns column names, types, and constraints

- `validate_schema(dataframe, expected_schema)` → `(bool, list[str])`:
  - Compares actual DataFrame columns against expected schema
  - Returns validation status and list of mismatches

- `get_column_mapping(filename, sheet_name)` → `dict`:
  - Returns column name to expected type mapping for a specific sheet

**Relationship**: Reads from `data/data_catalog.json` which is generated
by `scripts/generate_data_catalog.py`.

--------------------------------------------------------------------------------
7.8 Error Logger (backend/ingestion/error_logger.py)
--------------------------------------------------------------------------------

**Purpose**: Centralized logging for all ingestion pipeline errors.

**Functions**:

- `log_validation_error(row, column, error_type, details)`:
  - Records individual validation failures

- `log_ingestion_error(file, sheet, error)`:
  - Records file-level ingestion failures

- `get_error_summary(time_range)` → `dict`:
  - Returns aggregated error counts by type, file, and time period

--------------------------------------------------------------------------------
7.9 Defaults Module (backend/ingestion/defaults.py)
--------------------------------------------------------------------------------

**Purpose**: Provides default values and fallback configurations for the
ingestion pipeline.

**Constants**:
- Default column mappings for each known file type
- Expected data types per column
- Required vs optional column definitions
- Default values for missing fields (e.g., 0 for numeric, None for dates)

8. STAR SCHEMA DATABASE DESIGN
================================================================================

The ingestion pipeline loads data into a Star Schema analytical database
optimized for risk scoring queries and analytics.

--------------------------------------------------------------------------------
8.1 Dimension Tables
--------------------------------------------------------------------------------

**DimStudent** (canonical student dimension):
- `id` (PK): Internal student ID
- `username`: LMS username
- `email`: Student email
- `first_name`, `last_name`: Student name
- `department`: Academic department
- `is_active`: Current enrollment status
- **Source**: `Engagement_Analysis.xlsx` → "Learner Usage main dump" sheet

**DimCourse** (canonical course dimension):
- `id` (PK): Internal course ID
- `course_code`: Institutional course code
- `course_name`: Full course name
- `department_name`, `department_code`: Department info
- `semester_code`, `semester_name`: Term information
- `content_required`: Total content items in course
- `content_required_w1w2`: Week 1-2 content items
- **Source**: `Engagement_Analysis.xlsx` → "Courses" sheet

--------------------------------------------------------------------------------
8.2 Fact Tables
--------------------------------------------------------------------------------

**FactAcademicPerformance** (time-indexed academic facts):
- `student_id` (FK → DimStudent)
- `course_id` (FK → DimCourse)
- `trimester`: Academic term
- `quiz_score`, `assignment_score`, `exam_score`
- `exam_attendance`: Boolean attended flag
- `timestamp`: Measurement date
- **Source**: Quiz, assignment, and exam XLSX files

**FactEngagement** (time-indexed engagement facts):
- `student_id` (FK → DimStudent)
- `course_id` (FK → DimCourse)
- `content_completed`, `content_required`
- `quiz_completed`, `total_quiz_attempts`
- `discussion_posts_created`, `discussion_posts_read`, `discussion_posts_replied`
- `num_logins`, `total_time_spent_seconds`
- `assignment_submissions`
- `timestamp`: Measurement date
- **Source**: `Engagement_Analysis.xlsx`, weekly usage files

**FactConsistency** (consistency metrics):
- `student_id` (FK → DimStudent)
- `login_regularity_score`: Coefficient of variation for login patterns
- `study_streak_days`: Current consecutive study days
- `timestamp`
- **Source**: Computed from FactEngagement time series

**FactIntentResponsiveness** (intent and responsiveness signals):
- `student_id` (FK → DimStudent)
- `response_rate`: Rate of responding to outreach
- `intent_signal_score`: Computed intent indicator
- `timestamp`
- **Source**: Computed from intervention response data

--------------------------------------------------------------------------------
8.3 Data Lineage Table
--------------------------------------------------------------------------------

**DataLineage** (ETL audit trail):
- `id` (PK)
- `source_file`: Original filename
- `sheet_name`: Specific sheet processed
- `rows_processed`: Count of rows ingested
- `rows_quarantined`: Count of rows that failed validation
- `processing_start`, `processing_end`: Timestamps
- `status`: Success/failure/partial
- **Purpose**: Full audit trail for data governance and debugging

11. TROUBLESHOOTING
================================================================================

### Issue: "Student identifier not found"
**Cause**: File lacks required ID column
**Solution**:
1. Verify file is student-level (not aggregate)
2. Check for columns: `email`, `learner_email`, `Username`, `student_id`,
   `org_defined_id`
3. If aggregate file, move to separate reporting pipeline
4. Run `scripts/generate_data_catalog.py` to verify schema detection

### Issue: "Duplicate student records"
**Cause**: Multiple rows for same student
**Solution**:
1. Check if file contains time-series data (multiple timestamps)
2. If true duplicates, use latest record only
3. Check for different course sections (same student, different courses is OK)
4. The ingestion service uses `get_or_create` pattern to handle duplicates

### Issue: "Percentage validation failed"
**Cause**: Value outside expected range
**Solution**:
1. Check if percentages stored as decimals (0-1) or integers (0-100)
2. The `transformers.normalize_percentage()` auto-detects scale
3. Values > 100 or < 0 are quarantined
4. Verify source data quality in the original Excel file

### Issue: "Schema mismatch"
**Cause**: File structure changed from expected schema
**Solution**:
1. Re-run `scripts/generate_data_catalog.py` to update the catalog
2. Compare new catalog with previous version to identify changes
3. Update ingestion code if column names/types changed
4. Check if the header row detection found the correct row

### Issue: "Ingestion appears stuck / no new data"
**Cause**: Idempotency check preventing re-ingestion
**Solution**:
1. The `ingest_all_data()` function skips if students already exist
2. To force re-ingestion, clear the relevant database tables first
3. Check `DataLineage` table for last successful ingestion timestamp

13. DATA CATALOG (data_catalog.json)
================================================================================

File: `data/data_catalog.json` (~358KB)

This file is a programmatically generated catalog of all relevant data files
and their metadata. It is automatically created and updated by the
`scripts/generate_data_catalog.py` script.

**Purpose**:
  - **Schema Definition**: Provides a detailed, machine-readable schema for
    each sheet within every raw Excel file.
  - **Automated Validation**: Used by the backend's ingestion pipeline
    (`backend/ingestion/schema_manager.py`) to validate incoming data against
    expected columns, data types, and other constraints.
  - **Data Discovery**: Serves as a central repository for understanding
    the structure and content of raw data sources without needing to
    inspect each Excel file manually.
  - **Change Detection**: Can detect schema changes in raw data files,
    alerting data engineers to potential breaking changes.

**Content** (per raw data file):
  - `filename`, `filepath`
  - `analyzed_at` timestamp
  - A list of `sheets`, where each sheet entry includes:
    - `sheet_name`, `header_row` detected (0, 1, or 2)
    - `shape` (rows, columns), `row_count`, `column_count`
    - `student_identifier_columns` (auto-detected via keyword matching)
    - `time_columns` (auto-detected via keyword matching)
    - A detailed `columns` array, each with:
      - `name`: Column header
      - `dtype`: pandas data type (object, int64, float64, datetime64)
      - `null_count`: Number of null values
      - `null_percentage`: Percentage of nulls (0-100)
      - `unique_count`: Distinct non-null values
      - `sample_values`: First 3 non-null values

**Generation Command**: `python scripts/generate_data_catalog.py`

**Consumers**:
  - `backend/ingestion/schema_manager.py`
  - `backend/ingestion/pipeline.py`
  - `backend/services/core/data_ingestion.py`
