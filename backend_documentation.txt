================================================================================
1. PROJECT OVERVIEW
================================================================================

The EWS (Early Warning System) Retention Platform is a full-stack application
designed to predict student dropout risk from engagement data and automatically
trigger retention interventions. It is built for educational institutions
(specifically BITS Pilani Digital) to monitor student engagement across
multiple data sources and proactively intervene before students disengage.

The system works by:
  - Ingesting raw student engagement data from Excel spreadsheets (LMS usage,
    quiz scores, exam records, attendance data)
  - Computing 11+ engagement features per student using feature engineering
  - Calculating a weighted risk score (0-100) from those features
  - Mapping risk scores to intervention recommendations via a decision engine
  - Providing API endpoints for dashboards, predictions, business intelligence,
    and external integrations
  - Optionally using ML models (XGBoost, Random Forest) and Google Gemini AI
    for advanced predictions and personalized guidance

3. APPLICATION ENTRY POINT (main.py)
================================================================================

File: backend/main.py

This is the main entry point for the entire backend application.

WHAT IT DOES:
  - Creates a FastAPI application instance with title "EWS Retention Platform"
    version 2.0.0
  - Configures a lifespan context manager that runs on startup and shutdown
  - On STARTUP:
      1. Calls init_db() to create all database tables if they don't exist
      2. Opens a database session
      3. Calls ingest_all_data(db) to parse XLSX files and populate the
         database (this is idempotent - skips if data already exists)
  - On SHUTDOWN:
      Logs a shutdown message
  - Sets up CORS middleware allowing requests from configured origins
    (localhost:3000, localhost:8000, AI Advisor origin)
  - Includes the api_router with prefix "/api/v1" which mounts ALL route
    modules (students, predictions, llm, events, features, decisions,
    feedback, recommendations, advisor, business, integration)
  - Provides a root endpoint GET / that returns a welcome message with
    links to /docs and /redoc
  - When run directly, starts Uvicorn on the configured host and port
    (default 0.0.0.0:8000) with hot reload enabled

KEY FUNCTIONS:
  lifespan(app)       - Async context manager for startup/shutdown lifecycle
  read_root()         - GET / endpoint returning welcome JSON

6.1  STUDENTS API (backend/app/api/routes/students.py)
--------------------------------------------------------------------------------

Prefix: /api/v1/students

GET /overview
  Returns dashboard overview statistics:
    - total_students: total count of all students
    - at_risk_students: count of students with "high" risk category
    - average_risk_score: mean risk score across all students
    - risk_distribution: {low: N, medium: N, high: N}
    - total_enrollments: total enrollment records
    - total_courses: total course count
  Internally calls StudentService.get_overview_stats() which batch-fetches
  all enrollments, graded components, and exam records, then computes
  features and risk scores for every student.

GET /students
  Paginated list of all students with calculated metrics.
  Query Parameters:
    skip        (int, default 0)     - Pagination offset
    limit       (int, default 100)   - Page size
    sort_by     (str, default "risk_score") - Sort field
    order       (str, default "desc") - Sort order
    risk_min    (float, optional)    - Minimum risk score filter
    risk_max    (float, optional)    - Maximum risk score filter
  Returns list of student objects each containing:
    id, first_name, last_name, department, risk_score, risk_category,
    retention_likelihood, all 11 engagement scores, trend, per_course_breakdown

GET /students/{student_id}
  Detailed engagement information for a single student.
  Returns the same fields as the list endpoint but for one student.
  Returns 404 if student not found.

GET /at-risk
  Returns students above a risk threshold.
  Query Parameters:
    threshold   (float, default 60.0) - Risk score cutoff
    limit       (int, default 50)     - Maximum results
  Filters all students by risk_score >= threshold, sorted descending.

GET /risk-distribution
  Returns risk distribution across all students:
    - histogram: bucketed counts (0-10, 10-20, ..., 90-100)
    - percentiles: {p25, p50, p75, p90} risk score values
    - categories: {low, medium, high} counts

GET /courses
  Returns all courses with their content requirement counts:
    id, name, semester_code, semester_name, content_required_w1w2,
    content_required_total, week1_content, week2_content, lab_content

GET /courses/{course_id}/engagement
  Returns engagement breakdown for a specific course:
    - total_enrolled: number of students in the course
    - progress_categories: counts of students in "0%", "0-10%", ">10%"
    - avg_content_completed: average content items completed
    - avg_time_spent_hours: average time spent in hours

GET /analytics/trends
  Returns department-level and course-level analytics:
    - department_summary: [{department, student_count, avg_risk_score}]
    - course_summary: [{course, enrollments, avg_content_completed,
                        total_time_hours}]
    - total_analyzed: total students processed

GET /students/{student_id}/interventions
  Returns list of all interventions for a student:
    id, date, action, ai_suggested, ai_reasoning, effectiveness_score,
    risk_score_at_trigger, threshold_category, channels, assigned_team


--------------------------------------------------------------------------------
6.2  PREDICTIONS API (backend/app/api/routes/predictions.py)
--------------------------------------------------------------------------------

Prefix: /api/v1/predictions

GET /batch
  Batch risk predictions for all students.
  Query Parameters:
    include_decisions (bool, default False) - Include intervention recommendations
    limit            (int, default 100)    - Maximum results
  Returns list of prediction objects:
    student_id, risk_score (normalized 0-1), engagement_score,
    retention_likelihood, model_version ("rule_based_v2"),
    signal_breakdown: {academic, engagement, consistency, intent,
                       responsiveness} (all 0-1),
    top_risk_factors: list of weakest areas

  When include_decisions=True, also includes:
    recommended_intervention: {action_type, urgency, channels,
                               assigned_team, description}

GET /{student_id}
  Single student prediction with the same fields.
  Query Parameters:
    include_decisions (bool, default False)
  Returns 404 if student not found.

  Risk score normalization: The raw risk score (0-100) is divided by 100
  to produce a 0-1 probability for the API response.

  Intervention thresholds used in predictions:
    risk >= 0.80  -> urgent_intervention (sales, whatsapp, incentive)
    risk >= 0.60  -> mentor_outreach (faculty, email, mentor_call)
    risk >= 0.40  -> gentle_reminder (email)
    risk < 0.40   -> no_action

6.3  LLM API (backend/app/api/routes/llm.py)
--------------------------------------------------------------------------------

Prefix: /api/v1/llm

NOTE: Most of these endpoints currently return STUB/MOCK responses.
They are designed as the interface for future LLM integration.

POST /explain-risk-change
  Request: {student_id, time_period}
  Returns: AI-generated explanation of why a student's risk changed.
  Stub returns a mock explanation with key_factors and recommended_actions.

POST /student-advice
  Request: {student_id, question}
  Returns: Personalized advice for a student based on their data.

POST /faculty-summary
  Request: {student_id, for_role}

7.2  FEATURE ENGINEERING SERVICE (backend/app/services/feature_engineering.py)
--------------------------------------------------------------------------------

Class: FeatureEngineer

Derives engagement metrics from enrollment, graded component, and exam
data. All methods are @staticmethod and work with lists of dictionaries.

FEATURES COMPUTED (11 total):

1. CONTENT COMPLETION SCORE (0-100)
   Method: calculate_content_completion_score(enrollments)
   Formula: (total_content_completed / total_content_required) * 100
   Data: content_completed, content_required from each enrollment
   Meaning: What percentage of all required course content has the
   student completed? 100 = everything done, 0 = nothing touched.

2. W1&W2 COMPLETION SCORE (0-100)
   Method: calculate_w1w2_completion_score(enrollments)
   Formula: (capped_completed / total_w1w2_required) * 100
   Data: content_completed (capped at w1w2 amount), content_required_w1w2
   Meaning: How much of the critical first 2 weeks' content has the
   student completed? This is an early warning indicator since week 1-2
   engagement strongly predicts retention.

3. QUIZ ENGAGEMENT SCORE (0-100)
   Method: calculate_quiz_engagement_score(enrollments)
   Formula: (avg_quizzes_per_course / 20) * 100 + persistence_bonus
   Data: quiz_completed, total_quiz_attempts
   Normalization: 20 quizzes per course = 100% score
   Persistence bonus: If total_attempts > total_quizzes, adds up to
   10 bonus points (shows the student retries failed quizzes).
   Formula: min(10, (attempts/quizzes - 1) * 5)

4. DISCUSSION ENGAGEMENT SCORE (0-100)
   Method: calculate_discussion_engagement_score(enrollments)
   Formula: weighted_activity = (created*3) + (replies*2) + (read*0.5)
            score = (avg_weighted_per_course / 30) * 100
   Data: discussion_posts_created, discussion_post_replies,
         discussion_posts_read
   Weighting rationale: Creating posts shows highest engagement,
   replying shows moderate engagement, reading shows minimal engagement.

5. LOGIN CONSISTENCY SCORE (0-100)
   Method: calculate_login_consistency_score(enrollments)
   Formula: (avg_logins_per_course / 100) * 100
   Data: num_logins per enrollment
   Normalization: 100 logins per course = 100% score
   Meaning: How frequently does the student log into each course?

6. TIME INVESTMENT SCORE (0-100)
   Method: calculate_time_investment_score(enrollments)
   Formula: (avg_hours_per_course / 20) * 100
   Data: total_time_spent_seconds per enrollment
   Normalization: 20 hours per course = 100% score
   Meaning: How much time is the student investing in course content?

7. ASSIGNMENT SCORE (0-100)
   Method: calculate_assignment_score(enrollments)
   Formula: (avg_submissions_per_course / 5) * 100
   Data: num_assignment_submissions per enrollment
   Normalization: 5 submissions per course = 100% score

8. GRADED QUIZ SCORE (0-100)
   Method: calculate_graded_quiz_score(graded_components)
   Formula: average of (score/max_score * 100) for all quiz components
   Data: GradedComponent records where component_type='quiz'
   Missed quizzes (score=None or missed=True) count as 0%.
   Meaning: What is the student's average quiz grade?

9. GRADED ASSIGNMENT SCORE (0-100)
   Method: calculate_graded_assignment_score(graded_components)
   Formula: average of (score/max_score * 100) for all assignment components
   Data: GradedComponent records where component_type='assignment'
   Same logic as graded quiz score but for assignments.

10. EXAM SCORE (0-100)
    Method: calculate_exam_score(exam_records)
    Formula: average of (marks_obtained/marks_total * 100)
    Data: ExamRecord records
    Absent exams (present=False) count as 0%.
    Meaning: What is the student's average exam performance?

11. EXAM ATTENDANCE RATE (0-100)
    Method: calculate_exam_attendance_rate(exam_records)
    Formula: (attended_exams / total_exams) * 100
    Data: ExamRecord records, checking present field
    Meaning: What percentage of scheduled exams did the student attend?

DERIVED METRICS:

ZERO PROGRESS RATIO (0-1)
  Method: calculate_zero_progress_ratio(enrollments)
  Formula: count of courses with 0 content_completed / total courses
  Meaning: What fraction of courses has the student not started at all?
  Used as a penalty multiplier in risk scoring.

PROGRESS CATEGORY
  Method: get_progress_category(enrollments)
  Returns: "0%", "0-10%", or ">10%"
  Based on W1&W2 content completion percentage.

ENGAGEMENT TREND
  Method: get_engagement_trend(enrollments)
  Returns: "active", "declining", or "inactive"
  Logic:
    - inactive: total_logins=0 AND total_completed=0
    - declining: total_logins<10 OR total_completed<5
    - active: otherwise

PER-COURSE BREAKDOWN
  Method: get_per_course_breakdown(enrollments)
  Returns list of dicts, one per course, with:
    course_id, course_name, content_completed, content_required,
    completion_pct, quiz_completed, total_quiz_attempts,
    discussion_posts, time_spent_hours, logins, assignments_submitted

MASTER METHOD:
  calculate_all_features(enrollments, graded_components, exam_records)
  Calls all of the above methods and returns a single dictionary with
  all 11 scores + derived metrics. Defaults graded/exam scores to 0.0
  if no records provided.

7.3  RISK SCORING ENGINE (backend/app/services/risk_scoring.py)
--------------------------------------------------------------------------------

Class: RiskScorer

Calculates dropout risk from engagement features using a weighted formula.

ENGAGEMENT COMPONENT WEIGHTS (must sum to 1.0):
  content_completion    0.15   (15%)
  quiz_engagement       0.05   (5%)
  login_consistency     0.05   (5%)
  time_investment       0.05   (5%)
  discussion_engagement 0.05   (5%)
  assignment            0.05   (5%)
  graded_quiz           0.20   (20%)  <- highest weight
  graded_assignment     0.15   (15%)
  exam                  0.15   (15%)
  exam_attendance       0.10   (10%)

RISK THRESHOLDS:
  low:    < 40   (risk score below 40)
  medium: 40-70  (risk score 40 to 69)
  high:   >= 70  (risk score 70 and above)

METHODS:

calculate_risk_score(features) -> float (0-100)
  The core risk calculation:
  1. For each weight component, look up the corresponding feature score
  2. Compute weighted_engagement = sum(weight * score) for all 10 components
  3. Apply zero-progress penalty:
     If zero_progress_ratio >= 0.8 (80% of courses untouched),
     then weighted_engagement *= 0.5 (halved)
  4. risk_score = 100 - weighted_engagement
  5. Clamp to [0, 100]
  6. NaN safety check: if result is NaN, return 75.0 (default high-ish risk)

  EXAMPLE:
    If a student has weighted_engagement = 65.0 and zero_progress_ratio = 0.2:
    risk_score = 100 - 65.0 = 35.0 (low risk)

    If a student has weighted_engagement = 30.0 and zero_progress_ratio = 0.9:
    weighted_engagement = 30.0 * 0.5 = 15.0 (penalty applied)
    risk_score = 100 - 15.0 = 85.0 (high risk)

get_risk_category(risk_score) -> str
  Returns "low" (< 40), "medium" (40-69), or "high" (>= 70)

get_retention_likelihood(risk_score) -> str
  Maps risk to a human-readable label:
    < 20  -> "Very High" likelihood of retention
    < 40  -> "High"
    < 60  -> "Medium"
    < 80  -> "Low"
    >= 80 -> "Very Low"

get_dominant_risk_factor(features) -> str
  Identifies which engagement component is weakest (contributes most to risk).
  For each component: risk_contribution = (100 - score) * weight
  Returns the label of the component with the highest contribution.
  E.g., "Graded Quiz Performance" if quiz scores are lowest relative
  to their weight.

get_risk_breakdown(features) -> Dict
  Returns per-component risk values (100 - score for each) plus the
  weights dictionary. Used for detailed risk visualization.

validate_risk_score(risk_score) -> bool
  Validates that a risk score is a valid number in [0, 100].

7.4  DECISION ENGINE (backend/app/services/core/decision_engine.py)
--------------------------------------------------------------------------------

This module implements the risk threshold logic that maps risk scores
to concrete intervention actions.

NOTE: This module works with PROBABILITIES (0.0-1.0), not percentages.
The thresholds are imported from config.py.

THRESHOLDS (from config):
  THRESHOLD_NO_ACTION  = 0.30  (< 30%)
  THRESHOLD_GENTLE     = 0.60  (30-60%)
  THRESHOLD_MENTOR     = 0.80  (60-80%)
  THRESHOLD_URGENT     = 0.80  (>= 80%)

FUNCTIONS:

get_intervention_recommendation(risk_score: float) -> Dict
  Input: risk_score in [0.0, 1.0]
  Validates input (clamps to valid range, handles NaN/Inf)

  Returns one of 4 recommendations:

  RISK < 0.30 (No Action):
    action_type: "no_action"
    channels: []
    assigned_team: "none"
    urgency: "none"
    description: "Student is on track, no intervention needed"

  RISK 0.30-0.60 (Gentle Reminder):
    action_type: "gentle_reminder"
    channels: ["email"]
    assigned_team: "automated"
    urgency: "low"
    description: "Send automated email reminder to check in with student"
    message_template: "gentle_reminder_email"

  RISK 0.60-0.80 (Mentor Outreach):
    action_type: "mentor_outreach"
    channels: ["email", "mentor_call"]
    assigned_team: "faculty"
    urgency: "medium"
    description: "Assign faculty mentor for personalized outreach"
    message_template: "mentor_outreach_email"

  RISK >= 0.80 (Urgent Intervention):
    action_type: "urgent_intervention"
    channels: ["sales_call", "whatsapp", "incentive_offer"]
    assigned_team: "sales"
    urgency: "high"
    description: "Immediate escalation to sales team with multi-channel
                  outreach and incentive offer"
    message_template: "urgent_intervention_package"

should_trigger_intervention(current_risk, previous_risk, days_since_last)
  Determines whether to actually send an intervention:
  1. If risk >= THRESHOLD_NO_ACTION (0.30):
     a. If no recent intervention OR days_since_last >= COOLDOWN (7 days):
        -> Trigger = True
     b. If risk spike > RISK_SPIKE_THRESHOLD (0.15) compared to previous:
        -> Trigger = True (even during cooldown)
  2. Otherwise: Trigger = False

get_message_template(template_name, student_name) -> str
  Returns personalized email templates for each intervention type.
  Three templates available:
    gentle_reminder_email     - Friendly check-in
    mentor_outreach_email     - Mentor assignment notification
    urgent_intervention_package - Multi-channel support package

calculate_intervention_priority(risk_score, engagement_trend, days_inactive)
  Calculates queue priority:
    risk >= 0.85 + (declining trend OR inactive > 10 days) -> "critical"
    risk >= 0.85                                            -> "high"
    risk >= 0.70                                            -> "high"
    risk >= 0.45                                            -> "medium"
    else                                                    -> "low"

7.5  DATA INGESTION SERVICE (backend/app/services/core/data_ingestion.py)

This service parses raw XLSX files from data/raw/ and populates the

MASTER FUNCTION:

FUNCTION 2: _ingest_quiz_assignment_exam(db)

  b) _ingest_graded_sheet(db, wb, 'MSc Attendance', program='MSc')

       Col 2: ID No., Col 3: Email, Col 4: Name

       Col 13: Subject, Col 14: Subject Code

  c) _ingest_written_exam_marks(db, wb)
     Sheet: "Written Exam Marks"

     Column mapping: 5=email, 3=course_code, 8=student_name, 10=semester_info,
     15=total_marks, 16=obtained_marks.

  d) _ingest_exam_attendance(db, wb, 'Attendance-Slot-1', slot='slot-1')

  e) _ingest_exam_defaulters(db, wb)
     Sheet: "Exam Defaulter"
     Creates ExamRecord with present=False, course_code='EXAM_DEFAULT'
     for students with status "absent" or "activation pending".

FUNCTION 3: _update_enrollments_from_latest(db)

  a) graded quiz 1 10 feb complete.xlsx

--------------------------------------------------------------------------------
8.1  ML PREDICTOR (backend/ml/inference/predictor.py)
--------------------------------------------------------------------------------

This is the main ML prediction module that generates risk predictions
with comprehensive validation.

FUNCTIONS:

load_model()
  Loads the trained ML model via ModelRegistry. Called once and cached.

compute_signal_scores(features_df) -> Dict
  Computes 5 signal scores (all on 0-1 scale) from engineered features:
    academic:        Based on assignment_completion_rate, average_grade,
                     deadline_adherence_score, grade_trend
    engagement:      Based on login_frequency, avg_session_duration,
                     video_completion_rate, platform_interaction_score
    consistency:     Based on attendance_rate, activity_regularity_score
    intent:          Based on engagement_trend, days_inactive,
                     declining_performance_flag
    responsiveness:  Based on email_open_rate, message_reply_rate,
                     avg_response_time_hours

get_top_risk_factors(features_df, n=5) -> List[str]
  Extracts the top N risk factors by feature importance.
  Sorts features by their contribution to risk prediction.

predict_risk(student_data_df) -> Dict
  Main prediction function with 4 layers of validation:

  Layer 1: INPUT VALIDATION
    - Validates student_data is not empty
    - Checks required features exist

  Layer 2: FEATURE VALIDATION
    - Checks for NaN/Inf in features via validate_student_features()

  Layer 3: SANITIZATION
    - Replaces NaN/Inf with median/0 via sanitize_student_features()

  Layer 4: SAFE DEFAULTS
    - If model prediction fails, returns get_safe_default_prediction()

  Returns:
    risk_score:       0-100 (model probability * 100)
    prediction:       0 or 1 (binary classification)
    signal_breakdown: {academic, engagement, consistency, intent,
                       responsiveness} (all 0-1)
    top_risk_factors: list of strings
    prediction_error: boolean (true if fallback used)

  GUARANTEE: risk_score is always in [0, 100], never NaN/Inf/negative.

predict_with_explanation(student_data_df) -> Dict
  Prediction with explainable breakdown. Returns the prediction plus
  human-readable explanations for each signal.

simulate_risk_change(student_data_df, adjustments) -> Dict
  What-if simulation: applies adjustments to features and re-predicts.
  Returns current_risk, projected_risk, and risk_change.

SCALE CONVENTION:
  - Model outputs are probabilities (0-1)
  - Converted to percentage scale (0-100) for end-user display
  - Signal scores remain in probability scale (0-1)


--------------------------------------------------------------------------------
8.2  EXPLAINABLE RISK FORMULA (backend/ml/inference/risk_formula.py)
--------------------------------------------------------------------------------

This module provides a transparent, auditable risk calculation using
weighted signal formulas (as opposed to the black-box ML model).

FUNCTIONS:

get_signal_weights() -> Dict
  Returns the signal weights from config.py:
    academic: 0.30, engagement: 0.25, consistency: 0.20,
    intent: 0.15, responsiveness: 0.10
  Validates they sum to 1.0.

calculate_weighted_risk(signals: Dict) -> float
  Formula: risk = sum(weight_i * signal_i) for each of 5 signals
  Each signal_i is in [0, 1] where 1 = highest risk.
  Result is clamped to [0, 1].

get_risk_contribution_breakdown(signals: Dict) -> Dict
  For each signal, calculates:
    absolute_contribution = weight * signal_value
    percentage_of_total = (absolute / total_risk) * 100
  Returns breakdown showing exactly how much each signal contributes.

explain_risk_score(risk_score, signals) -> Dict
  Generates a human-readable explanation:
    risk_score, risk_category, explanation text, signal_details,
    contributing_factors (signals above 0.5), protective_factors
    (signals below 0.3)

  Risk Categories:
    < 0.30  -> "Low Risk" (on track)
    0.30-0.60 -> "Moderate Risk" (showing warning signs)
    0.60-0.80 -> "High Risk" (at significant risk)
    >= 0.80 -> "Critical Risk" (requiring immediate attention)

simulate_what_if(current_signals, adjustments) -> Dict
  Applies hypothetical changes to signals and recalculates risk.
  Returns: current_risk, projected_risk, risk_change, adjustments_applied

9.2  ACADEMIC SIGNALS (backend/features/academic_signals.py)
--------------------------------------------------------------------------------

Class: AcademicPerformanceSignal(SignalComputer)

Computes academic performance risk signal from quiz and exam data.

WEIGHTS:
  quiz_completion_rate:  0.3  (30%)
  quiz_average_score:    0.3  (30%)
  exam_participation:    0.2  (20%)
  exam_score:            0.2  (20%)

METHOD: compute(db_session, student_id, trimester) -> float (0-100)
  1. Queries FactAcademicPerformance table for quiz and exam records
  2. Computes 4 sub-metrics:
     - quiz_completion_rate: % of quizzes submitted
     - quiz_average_score: average quiz score percentage
     - exam_participation: exam attendance rate
     - exam_average_score: average exam score percentage
  3. Computes weighted score
  4. INVERTS the result: risk = 100 - score
     (low performance = high risk)


--------------------------------------------------------------------------------
9.3  ENGAGEMENT SIGNALS (backend/features/engagement_signals.py)
--------------------------------------------------------------------------------

Class: EngagementSignal(SignalComputer)

Computes engagement risk signal from platform activity data.

WEIGHTS:
  attendance_rate:       0.5  (50%)
  platform_time:         0.3  (30%)
  content_interaction:   0.2  (20%)

METHOD: compute(db_session, student_id, trimester) -> float (0-100)
  1. Queries FactEngagement table
  2. Computes 3 sub-metrics:
     - avg_attendance: average attendance_percentage
     - platform_engagement: normalized to 0-100 (120 min/week = 100%)
     - content_score: normalized to 0-100 (20 items/week = 100%)
  3. Computes weighted score
  4. INVERTS the result: risk = 100 - score


--------------------------------------------------------------------------------
9.4  TEMPORAL FEATURES (backend/features/temporal_features.py)
--------------------------------------------------------------------------------

Class: TemporalFeatureComputer

Detects deteriorating patterns over time before they become critical.

METHODS:

compute_all(db, student_id) -> Dict
  Runs all temporal feature computations and returns combined results.

grade_trend_slope(db, student_id) -> Dict
  Uses linear regression on the last 5 assessment scores.
  Returns: value (slope), interpretation, risk_level
    Negative slope = declining performance
    risk_level: "high" if slope < -5, "medium" if < 0, "low" otherwise

score_volatility(db, student_id) -> Dict
  Standard deviation of last 5 scores.
  Returns: value, interpretation, risk_level
    High volatility (> 20) = inconsistent performance = medium risk

recent_vs_historical_delta(db, student_id) -> Dict
  Compares average of last 3 scores vs overall historical average.
  Returns: value (delta), interpretation, risk_level
    Negative delta = recent decline

engagement_decay_rate(db, student_id) -> Dict
  Week-over-week percentage decline in platform time (from FactEngagement).
  Returns: value (% decline per week), interpretation, risk_level
    > 20% decline = high risk
    > 10% decline = medium risk

longest_inactivity_gap(db, student_id) -> Dict
  Maximum consecutive days without login within a 30-day window.
  Returns: value (days), interpretation, risk_level
    > 7 days = high risk
    > 3 days = medium risk

session_frequency_trend(db, student_id) -> Dict
  Linear regression slope of logins-per-week over the last 4 weeks.
  Returns: value (slope), interpretation, risk_level
    Negative slope = decreasing engagement


--------------------------------------------------------------------------------
9.5  BEHAVIORAL FEATURES (backend/features/behavioral_features.py)
--------------------------------------------------------------------------------

Class: ConsistencyFeatureComputer

Measures the regularity and consistency of student behavior.

METHODS:

login_regularity_score(db, student_id) -> Dict
  Coefficient of variation of daily login counts.
  Low CV = consistent = low risk. High CV = erratic = high risk.
  Inverted to 0-100 scale where 100 = perfectly regular.

study_streak_strength(db, student_id) -> Dict
  Current consecutive days with > 20 minutes of activity.
  Long streaks = good habits = low risk.

recovery_speed(db, student_id) -> Dict
  Average days to recover activity after inactivity gaps of 5+ days.
  Fast recovery = resilient. Slow recovery = concerning.

weekend_weekday_ratio(db, student_id) -> Dict
  Ratio of weekend to weekday activity time.
  Very low ratio might indicate disengagement on weekends.
  Ideal ratio is around 0.5-1.5.

late_night_ratio(db, student_id) -> Dict
  Percentage of activity occurring between 11pm and 5am.
  High ratio might indicate poor time management.
  (Requires detailed timestamp data in FactEngagement.)


Class: EffortOutcomeFeatureComputer

Measures the relationship between effort invested and outcomes achieved.

METHODS:

time_to_score_ratio(db, student_id) -> Dict
  Platform minutes invested per percentage point earned.
  High ratio = lots of effort for little result = might need support.
  Low ratio = efficient learning.

retake_improvement(db, student_id) -> Dict
  Average improvement on retaken assessments.
  Positive improvement = learning from mistakes.
  Requires attempt_number in FactAcademicPerformance.

practice_exam_gap(db, student_id) -> Dict
  Difference between quiz average and exam score.
  Large negative gap = performs worse in exams than quizzes.
  May indicate exam anxiety or different testing conditions.

procrastination_index(db, student_id) -> Dict
  Percentage of assignments submitted in the last 20% of the deadline window.
  High procrastination = poor time management = medium-high risk.


--------------------------------------------------------------------------------
9.6  COMPOSITE INDICES (backend/features/composite_indices.py)
--------------------------------------------------------------------------------

Class: CompositeIndexComputer

Combines multiple advanced features into interpretable composite risk scores.

4 COMPOSITE INDICES:

1. DISENGAGEMENT VELOCITY INDEX (DVI) (0-100)
   Measures the RATE at which a student is disengaging.

   Components and weights:
     engagement_decay_rate:     0.30  (30%)  - How fast engagement drops
     session_frequency_trend:   0.25  (25%)  - Login frequency change
     longest_inactivity_gap:    0.20  (20%)  - Longest absence
     login_regularity:          0.15  (15%)  - Consistency of logins
     response_latency:          0.10  (10%)  - Response to communications

   Risk levels:
     DVI < 30:  "Stable" engagement
     DVI 30-60: "Moderate" decline
     DVI > 60:  "Rapid" disengagement

2. ACADEMIC INSTABILITY INDEX (AII) (0-100)
   Measures volatility and instability in academic performance.

   Components and weights:
     score_volatility:          0.30  (30%)  - Score variation
     grade_trend:               0.25  (25%)  - Grade trajectory
     practice_exam_gap:         0.20  (20%)  - Quiz vs exam difference
     efficiency:                0.15  (15%)  - Time-to-score ratio
     procrastination:           0.10  (10%)  - Late submissions

   Risk levels:
     AII < 30:  "Stable" academic performance
     AII 30-60: "Some instability" detected
     AII > 60:  "High instability" in performance

3. ROUTINE STRENGTH INDEX (RSI) (0-100)
   Measures the strength and consistency of study habits.
   NOTE: Higher = better (unlike other indices where higher = worse).

   Components and weights:
     login_regularity:          0.30  (30%)  - Login consistency
     study_streak:              0.25  (25%)  - Consecutive active days
     weekend_weekday_balance:   0.20  (20%)  - Even distribution
     recovery_speed:            0.15  (15%)  - Bounce-back ability

   Risk levels:
     RSI > 70:  "Strong" routine
     RSI 40-70: "Moderate" routine
     RSI < 40:  "Weak" routine

4. RETENTION RISK INDEX (RRI) (0-100) -- MASTER INDEX
   The overall dropout risk combining all other signals.

   Components and weights:
     DVI:                       0.30  (30%)  - Disengagement velocity
     AII:                       0.25  (25%)  - Academic instability
     response_latency:          0.15  (15%)  - Communication response
     ignored_escalations:       0.15  (15%)  - Ignored interventions
     RSI (inverted):            0.10  (10%)  - Routine weakness
     refund_inquiries:          0.05  (5%)   - Financial disengagement

   Risk levels and recommended actions:
     RRI < 30:   LOW - "Continue standard engagement monitoring"
     RRI 30-60:  MODERATE - "Implement gentle outreach. Increase check-in
                  frequency. Monitor closely."
     RRI 60-80:  HIGH - "Immediate mentor outreach. Multi-channel
                  intervention. Weekly check-ins."
     RRI > 80:   CRITICAL - "Emergency intervention. Sales team engagement.
                  Incentive package. Daily monitoring."

   Each index returns:
     value: numeric score (0-100)
     risk_level: text label
     components: dict of component values and weights
     interpretation: human-readable description

9.7  ADVANCED RISK SCORER (backend/features/risk_scorer.py)
--------------------------------------------------------------------------------

Class: RiskScorer (in features/ module, different from services/ RiskScorer)

Aggregates advanced signal computations into a final risk score.

SIGNAL WEIGHTS:
  academic_performance:  0.45  (45%)
  engagement:            0.55  (55%)

METHOD: compute_risk_score(db_session, student_id, trimester) -> Dict

  1. Computes AcademicPerformanceSignal
  2. Computes EngagementSignal
  3. Computes weighted average
  4. Applies MULTI-LAYER BOUNDS CHECKING:
     a. Clamp to [0, 100]
     b. Validate is a valid number
     c. Check for NaN/Inf (replace with 50.0)

  Returns:
    risk_score:     float (0-100)
    risk_level:     "Low" (<25), "Medium" (25-50), "High" (50-75),
                    "Critical" (>=75)
    signals:        {academic_performance, engagement}
    missing_signals: list of signals that couldn't be computed
    confidence:     float (0-1) = percentage of available signals

  Tracks and reports errors during data ingestion:
  - Counts by error type
  - Stores detailed error records with row/column context
  - Generates summary reports

quarantine.py:
  Handles invalid records that fail validation:
  - Stores quarantined records separately
  - Tracks reason for quarantine
  - Allows review and re-processing

defaults.py:
  Defines default values for missing data:
  - Missing scores default to None (not 0)
  - Missing dates default to None
  - Missing boolean flags default based on context

  Simple header-based auth (should use JWT in production).

  Returns a FastAPI dependency that checks if the current user's role
  has sufficient permissions.

  Role hierarchy: student < faculty < admin

  Example usage:
    @router.get("/admin-only", dependencies=[Depends(require_role("admin"))])

  Raises HTTP 403 if the user's role is below the required level.

13. SCALE CONVENTIONS & IMPORTANT NOTES
================================================================================

SCALE CONVENTIONS:

  Risk Scores:
    0-100 scale (percentage) for end-user display and API responses
    0-1 scale (probability) used internally by decision engine and
    ML predictor signal breakdowns

  Signal Scores:
    Always 0-1 scale (probability)
    Higher value = HIGHER risk (for academic, engagement, etc.)

  Engagement Feature Scores:
    0-100 scale
    Higher value = BETTER engagement (inverse of risk)

  Conversion:
    risk_score_pct = model_probability * 100
    engagement_risk = 100 - engagement_score

RISK CATEGORY MAPPINGS (multiple systems, slightly different thresholds):

  Risk Scoring Engine (services/risk_scoring.py):
    Low:    < 40
    Medium: 40-69
    High:   >= 70

  Decision Engine (services/core/decision_engine.py):
    No Action:      < 30% (0.30)
    Gentle Reminder: 30-60% (0.30-0.60)
    Mentor Outreach: 60-80% (0.60-0.80)
    Urgent:         >= 80% (0.80)

  Risk Formula (ml/inference/risk_formula.py):
    Low:      < 30%
    Moderate: 30-60%
    High:     60-80%
    Critical: >= 80%

  Advanced Risk Scorer (features/risk_scorer.py):
    Low:      < 25
    Medium:   25-50
    High:     50-75
    Critical: >= 75

VALIDATION STRATEGY:
  The system implements defense-in-depth validation:
  1. Input validation: Check raw data before processing
  2. Feature validation: Check computed features for NaN/Inf
  3. Score validation: Clamp all scores to valid ranges
  4. Output validation: Validate API responses before returning
  5. Safe defaults: Return neutral predictions (50% risk) on failures

IDEMPOTENCY:
  Data ingestion is idempotent - it checks if data already exists
  before processing. Running the server multiple times won't
  duplicate data.

ERROR HANDLING:
  - All services log errors with descriptive messages
  - Data ingestion failures roll back the entire transaction
  - ML prediction failures return safe default predictions
  - Invalid risk scores are clamped to valid ranges
  - NaN/Inf values are detected and replaced
